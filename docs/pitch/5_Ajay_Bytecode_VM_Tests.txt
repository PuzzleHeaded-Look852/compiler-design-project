READ THIS FIRST: WHAT THE PROJECT IS (even if you did nothing)
------------------------------------------------------------
Lumen is a small programming language we built, plus the compiler for it. In most languages a number is just a
number: 9.8 could be metres, seconds or dollars. In Lumen a number carries its unit: "9.8 m/s^2", "12.5 lbf*s",
"250 USD". The compiler checks units like a physics teacher checks working. After the check the units are erased,
so the program that runs is plain arithmetic.

Why it matters: NASA lost the $327.6 million Mars Climate Orbiter in 1999 because one program gave pound-force
seconds and another read newton-seconds (a factor of 4.45). An Air Canada 767 ran out of fuel in 1983 because 1.77
(pounds per litre) was used as kg per litre. To an ordinary compiler these are just "float". In Lumen both are
compile errors.

The compiler is a pipeline of seven phases:
  lexer -> parser -> unit checker -> intermediate code -> optimizer -> BYTECODE -> VIRTUAL MACHINE
The first five phases read, check and simplify the program. YOUR phases are the last two: turn the simple code
into instructions for a small imaginary computer (bytecode), and then be that computer (the VM) and actually run
it. Your files: codegen.py (about 158 lines), vm.py (about 156 lines), the tests folder, and the web playground in
the playground folder (server.py about 187 lines, index.html about 350 lines).

[PHASE 6: BYTECODE]
"The target is a small stack machine. Think of a pile of plates. To add two numbers you put both on the pile, then
the ADD instruction takes the top two off and puts the answer back. So 't3 equals t1 times t2' becomes: LOAD t1,
LOAD t2, MUL, STORE t3."
"The whole instruction set is small. PUSH puts a constant on the stack. LOAD and STORE move values between the stack
and a variable's slot. Then the arithmetic and comparison operations: ADD, SUB, MUL, DIV, MOD, POW, LT, LE, GT, GE,
EQ, NE, plus NEG, NOT and I2F, which turns an int into a float. JMP, JZ and JNZ are jumps. CALL calls a Lumen
function, CALLB calls a built-in like sqrt, RET returns, POP discards a value and PRINT prints."
"Each variable and temporary gets a numbered slot in its function's frame. Labels become absolute addresses in a
second pass."
[DEMO 1: show fib's bytecode, command below]
"Here is the Fibonacci function. LOAD n, PUSH 2, LT is 'n less than 2'. JZ jumps past the return if it is false.
Then it computes n minus 1 and CALLs fib, computes n minus 2 and CALLs fib again, ADDs the two results and RETurns.
Notice there is not a single unit anywhere in the bytecode. A unit conversion is just PUSH a factor, then MUL, and
usually the optimizer has already folded even that away."

[PHASE 7: THE VIRTUAL MACHINE]
"The virtual machine is a classic fetch, decode, execute loop. Each function call gets a frame, which holds that
function's local slots, its own operand stack and an instruction pointer. CALL pushes a new frame. RET pops it and
hands the result to the caller's stack."
"One design decision is worth explaining. The frames live in my own list, not on Python's call stack. So when a
Lumen program recurses too deeply, I can count the depth and stop cleanly. The limit is 5000 nested calls and the
error is a clear Lumen message, not a Python crash."
"The VM also protects against infinite loops with a step limit of ten million instructions. And every runtime error
carries the source line."
[DEMO 2: runtime errors, commands below]
"First, a program that divides by zero. It compiles fine, because the checker cannot always know the value, and the
first call prints 5. The second call stops with 'division by zero' and shows the exact line. Next, a function that
calls itself forever: 'call stack too deep, more than 5000 nested calls'. And a while-true loop is stopped by the
step limit. The exit code for all of these is 3. The built-in functions are sqrt, abs, minimum, maximum, float and
int, and sqrt of a negative number is also a clean runtime error."

[ZERO RUNTIME COST: THE EVIDENCE]
"The central claim of the project is that units cost nothing at run time. The evidence is in the structure. The VM
and the code generator contain no unit logic at all. The VM only knows ints, floats, booleans and strings. And we
have a test that compiles a program with units, 'let v: km/h = 10 m/s', and the same program written with the plain
number 36.0, and checks the optimized code is identical. The units were checked, and then they were gone."

QUESTIONS THE PROFESSOR MAY ASK, AND SHORT ANSWERS
------------------------------------------------------------
Q: Are units really free at run time?
A: Yes. By the time we generate bytecode every unit has been checked and erased. The VM only knows ints, floats,
   bools and strings, and a conversion is just a multiply by a constant that the optimizer usually folds away.

Q: Why a stack machine and not registers?
A: A stack machine is the simplest target: code generation is almost mechanical, and it is easy to explain.

Q: Why keep your own frames instead of using Python recursion?
A: So we can limit the depth and report a clean Lumen error. Python's own recursion limit would crash with a
   Python traceback.

Q: How does the VM handle an infinite loop?
A: Every instruction counts as a step. After 10,000,000 steps it stops with "step limit exceeded (infinite loop?)"
   and the line number. Exit code 3.

Q: What is a golden test?
A: We record the correct output of each of the 34 examples once, in tests/golden. The test reruns each example and
   compares with the recorded output. If anything changes by accident, the test fails.

Q: How do you know the optimizer is safe?
A: The test suite runs the example programs with and without the optimizer and compares the output. They must match.
   (Noel can explain the safety rules.)

Q: What does CALLB do?
A: It calls a built-in function: sqrt, abs, minimum, maximum, float or int. CALL calls a function written in Lumen.

Q: Why is it slow, and does that matter?
A: The VM is written in Python, which is slow. For a teaching language that is fine. A native back end such as LLVM is
   listed as future work.

Q: How does the playground work?
A: A tiny Python web server (standard library only) imports the real compiler. The page sends the code, the server
   runs every phase and returns each phase's output as text, and the page shows it in tabs. Nothing is faked.
