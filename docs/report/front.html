Abstract

Ordinary programming languages treat a number as just a number, so a program can add metres to seconds, or pass pounds where kilograms were expected, and no compiler will object. Unit mistakes of exactly this kind caused the loss of NASA's Mars Climate Orbiter in 1999 and the fuel exhaustion of Air Canada Flight 143 in 1983. This case study examines Lumen, a small statically typed language in which every number carries its unit, together with a complete hand-written compiler for it.

The compiler has seven phases: a lexer, a recursive-descent parser with two context rules that tell units from variables, a unit and type checker that computes the dimension of every expression as a synthesized attribute, a three-address code generator, an optimizer, a bytecode generator and a stack-based virtual machine. Compatible units are converted automatically using exact rational arithmetic; incompatible ones are rejected with a located error message and a suggested fix. After checking, units are erased, so the program that runs contains no unit logic at all, and the optimizer folds conversions into constants.

The study documents the design from the source code (3,437 lines of Python, no third-party dependencies), reproduces the test suite (187 of 187 tests pass, with golden outputs for 34 example programs), and measures compilation at about 0.16 ms for a 10-line program and 49 ms for a 1,603-line program. It reproduces the Mars and Gimli bugs as compile-time errors. It also states what Lumen does not do: it checks one program at a time, has no temperature units, tracks dimensions rather than quantity kinds, and runs on a Python virtual machine. A roadmap for future work closes the study.

Keywords: compiler design, units of measure, dimensional analysis, type checking, syntax-directed definition, three-address code, code optimization, stack virtual machine.
