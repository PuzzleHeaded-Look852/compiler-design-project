1. Introduction

1.1 Background

Every programming language a student learns treats a number as just a number. To int and float, five metres, five seconds and five kilograms are the same value: 5. The program is allowed to add them, compare them, or pass a time where a distance was expected, and nothing complains until the answer is wrong. The unit lives only in a variable name or a comment, and the compiler never reads either.

This is a real engineering problem, not a classroom one. NASA lost the Mars Climate Orbiter in 1999 because one program produced thruster impulse in pound-force seconds and another read the same numbers as newton seconds, an error of a factor of 4.45 [7]. In 1983 an Air Canada Boeing 767 ran out of fuel in flight because a conversion factor in pounds per litre was used where kilograms per litre was needed [8]. In both cases every value had the right type as far as the software could tell. Only its unit was wrong, and no type checker was looking at units.

1.2 Project Overview

Lumen is a small, statically typed programming language in which every number carries its unit. 9.8 m/s^2, 12.5 lbf*s and 250 USD are values of different types. We also wrote the complete compiler for it in Python, by hand, with no parser generators and no third-party libraries apart from pytest for testing. The compiler is 3,437 lines of Python in 16 modules.

The compiler works in seven phases. The first three understand the program: a lexer, a recursive-descent parser and a unit and type checker that works out the dimension of every expression, converts compatible units exactly and rejects incompatible ones with a precise message. After that the units are erased. The last four phases (three-address code, an optimizer, a bytecode generator and a stack-based virtual machine) see only plain numbers, so the checking costs nothing while the program runs.

1.3 Purpose and Organization of This Case Study

This case study describes the problem Lumen addresses, the language, the seven phases of the compiler, the way it was tested, and what it measured. It also states plainly where the design stops. Sections 2 to 4 cover the problem and background. Sections 5 to 9 describe the design and the implementation. Sections 10 and 11 cover testing and measurement. Sections 12 to 15 discuss contributions, limitations, future work and conclusions.

Every technical statement in this report was checked against the source code, and every program output shown was produced by running the compiler. Where the project's own documents say more than the code shows, the code is treated as correct and the difference is recorded in Section 13.

2. Problem Statement

Four weaknesses of ordinary languages and tools motivated the project. Each one is a design problem, not just a missing feature.

2.1 Numbers Without Units

A type system that only knows int and float cannot tell length from time. The expression distance + time is as meaningless as adding a word to a number, but it compiles in C, Java, Python and Go. Unit errors are therefore found by testing or by accident, never by the compiler, even though they are exactly the kind of mistake a type checker exists to catch.

2.2 Silent Conversion Errors

Even when programmers know the units, they convert them by hand: multiply by 1000, divide by 3600, multiply by 4.448. Each hand conversion is a chance to use the wrong factor, apply it twice, or forget it. The Mars and Gimli failures were both conversion errors. In medicine the same mistake appears as microgram/milligram confusion; one hospital study found it to be the most common medication-error type, in 34.8% of the patients studied [9]. Everyday software has small versions of the same bug: a timeout set in milliseconds where seconds were meant, or MB/s confused with Mbit/s (a factor of 8).

2.3 Unit Libraries Are Rarely Used

Libraries that attach units to numbers exist for most languages, but practitioners avoid them. A 2022 study of the area reports that developers find them inconvenient: extra syntax, poor interaction with the rest of the program, performance costs, and in some cases checking only at run time [3]. The same study argues that a solution built into the language works better than a library added on top.

2.4 Engineering Question

Can a small language make units part of the type of every number, check them completely at compile time, convert between compatible units exactly, give error messages a student can act on, and still produce a running program that contains no unit logic at all? Lumen is the attempt to answer that question, built so that each phase also illustrates a topic of the Compiler Design syllabus.

3. Objectives and Scope

3.1 Objectives

  1. Design a small, C-like, statically typed language in which a number literal can carry a unit, and units can appear as types of variables, parameters and function results.
  2. Check the dimension of every expression at compile time using dimension algebra: multiplication adds dimension exponents, division subtracts them, and addition requires them to be equal.
  3. Convert between units of the same dimension automatically and exactly, using rational arithmetic rather than rounded decimals.
  4. Erase units after checking, so the intermediate code, the bytecode and the virtual machine contain no unit logic.
  5. Report every lexical, syntax, unit and runtime error with a line, a column, a caret under the problem and a suggested fix, never a Python traceback.
  6. Make every phase visible through a command-line flag, and verify the system with an automated test suite.

3.2 In Scope

  • A hand-written lexer and recursive-descent parser, with error recovery so that one run reports several errors.
  • Base units m, kg, s and bit, SI prefixes, user-declared units (unit h = 3600 s;) and user-declared base dimensions such as currencies (unit INR;).
  • A unit and type checker that inserts explicit conversion nodes, and a three-address code generator, optimizer, bytecode generator and stack virtual machine.
  • 34 example programs, including the Mars Climate Orbiter and Gimli Glider bugs written in Lumen, with recorded expected outputs.
  • A small local web playground that runs the compiler and shows the output of each phase.

3.3 Out of Scope

  • Checking units across separate programs or files. Lumen checks one program at a time (Section 13).
  • Offset units such as degrees Celsius and Fahrenheit, which need more than a scale factor.
  • Arrays, structures, pointers, modules, and a native machine-code back end.

4. Background and Related Work

4.1 Compiler Phases

The classical structure of a compiler splits the work into lexical analysis, syntax analysis, semantic analysis, intermediate code generation, optimization and target code generation [1]. The lexer turns characters into tokens. The parser checks the tokens against a grammar and builds a tree. Semantic analysis checks meaning, such as whether names are declared and types agree. The intermediate code generator lowers the tree to a machine-independent form such as three-address code, which the optimizer improves before the code generator produces the target. Lumen follows this structure exactly, with a virtual machine as the target.

4.2 Dimensional Analysis

Physicists check equations by their dimensions: a speed is a length divided by a time, so any formula for a speed must reduce to length1·time-1. A dimension can be written as a vector of integer exponents over a set of base dimensions. Multiplying two quantities adds their vectors, dividing subtracts them, and raising to a power multiplies the vector. Two quantities can only be added or compared if their vectors are equal. A unit is a dimension plus a scale: a kilometre is a length with scale 1000 relative to the metre. Kennedy showed how these rules fit inside a type system [2], and F# ships them as a language feature [13].

4.3 Syntax-Directed Definitions

A syntax-directed definition attaches attributes to grammar symbols and gives rules for computing them [1]. When every attribute of a node is computed from the attributes of its children, the definition is S-attributed and can be evaluated in one bottom-up (post-order) walk of the tree. Lumen's checker is exactly this: the attribute is the type of each expression, made of a kind, a dimension and a scale, and each operator has a rule that computes the parent's type from its children's.

5.3 Design Principles

  • Units never reach run time. The code generator and virtual machine contain no unit logic; a unit conversion is already an ordinary multiplication when it reaches them.
  • Scales are exact. Conversion factors are Python Fraction values [14] until the last step, so converting km to m and back to km gives a factor of exactly 1.
  • One arithmetic. The optimizer and the virtual machine use the same function to evaluate operators, so an optimized program always prints the same result as the unoptimized one. Operations that can fail at run time, such as division by a value that might be zero, are never folded or deleted.
  • Errors are collected, not thrown. Every phase records problems and carries on. An expression with an error gets a special error type and stays silent afterwards, so one mistake produces one message, not a cascade.
  • Conversion changes scale, never dimension. km can become m automatically; a plain number never becomes a quantity, and a length never becomes a time.

6. The Lumen Language

6.1 A First Program

The program below shows most of the language. A number followed by a unit is a quantity. Units can be declared, can be used as types, and can be converted explicitly with in. The last line is rejected at compile time.

unit min = 60 s;                      // a unit declared from another
unit h   = 3600 s;

fn pace(d: km, t: min) -> km/h {      // units as parameter and result types
    return d / t;                     // km/min converted to km/h
}

fn main() {
    let d = 42.195 km;
    let t = 3 h + 30 min;             // mixed scales: t is in h
    print(pace(d, t));                // 12.055714286 km/h
    print(d in m);                    // explicit conversion: 42195.0 m
    let x = d + 5 s;                  // ERROR: length + time
}

6.2 Lexical Rules and Grammar

Identifiers, numbers, strings, comments and operators follow C-like rules. The keywords are fn let if else while return print true false unit in int float bool string. A float needs digits on both sides of the dot, and every number keeps its exact value as a fraction, so 0.1 is exactly one tenth. The grammar, in EBNF, is:

program    = { unitDecl | function } EOF
unitDecl   = "unit" IDENT ( ";" | "=" NUMBER unitExpr ";" )
function   = "fn" IDENT "(" [ param { "," param } ] ")" [ "->" type ] block
type       = "int" | "float" | "bool" | "string" | unitExpr
unitExpr   = unitFactor { ( "*" | "/" ) unitFactor }
unitFactor = ( IDENT | "(" unitExpr ")" ) [ "^" [ "-" ] INT ]
statement  = let | assign | if | while | return | print | block | exprStmt
expr       = logicOr [ "in" unitExpr ]
logicOr    = logicAnd { "||" logicAnd }
logicAnd   = equality { "&&" equality }
equality   = comparison { ("=="|"!=") comparison }
comparison = term { ("<"|"<="|">"|">=") term }
term       = factor { ("+"|"-") factor }
factor     = unary { ("*"|"/"|"%") unary }
unary      = ("-"|"!") unary | power
power      = primary [ "^" [ "-" ] INT ]
primary    = NUMBER [ unitLiteral ] | STRING | "true" | "false"
           | IDENT [ "(" [ expr { "," expr } ] ")" ] | "(" expr ")"

Precedence comes from the layering of the rules, and loops replace left recursion so the grammar stays LL(1). Units need two context rules, which are the most interesting parsing problem in the project. First, a name directly after a number is a unit: in 5 km, km is a unit, and no other construct puts a name there. Second, a unit literal continues over * or / only if the next name is a known unit: 9.8 m/s^2 is one literal, but 10 m / t, where t is a variable, is (10 m) / t. This is the same kind of problem as C's well-known typedef ambiguity, solved by consulting a table of known names during parsing.

6.3 Units and Dimensions

  • Dimension: what kind of quantity a value is, stored as exponents over base units. Speed is m1·s-1.
  • Unit: a dimension plus an exact scale. km is length with scale 1000; h is time with scale 3600.
  • Base units: m (length), kg (mass), s (time), bit (data), and the built-in g = 1/1000 kg. SI prefixes n u m c k M G attach to m s g bit (km, mg, ms, Mbit).
  • Declared units: unit lbf = 4.4482216152605 N; defines a unit from existing ones.
  • New base dimensions: unit INR; creates a dimension of its own. INR and USD can never be added or converted by accident; a rate must be written with its own unit (83.5 INR/USD).

6.4 Typing Rules

Every expression has a type made of a kind (int, float, bool, string), a dimension and a scale. Table 4 gives the rules the checker applies.

Table 4: Unit typing rules
ExpressionRule
a + b, a - b, a < b, a == bDimensions must be equal. If the scales differ, the right side is converted to the left side's unit (1 km + 500 m is 1.5 km).
a * bDimensions add, scales multiply (3 m * 4 m is 12 m^2).
a / bDimensions subtract, scales divide. If everything cancels, the result is a plain number (2 km / 500 m is 4).
a ^ nn is an integer literal; dimension and scale are raised to n.
x in UExplicit conversion; an error unless x and U have the same dimension.
let, assignment, argument, returnSame dimension required; scale differences converted automatically. A plain number never becomes a quantity, except the literal 0.
sqrt(q)Every exponent of q's dimension must be even (sqrt(9 m^2) is 3 m).

The other rules are the usual ones for a C-like language: conditions must be bool; int widens to float but never narrows implicitly; names must be declared before use; blocks create scopes and may shadow outer names; a function with a result type must return on every path; and the program must contain fn main().

7. The Seven-Phase Compiler Pipeline

This section follows one program through every phase. All outputs below are real compiler output for the program in examples/phases_demo.lum:

unit h = 3600 s;

fn main() {
    let d = 90 km;
    let t = 1.5 h;
    let v = d / t;
    print(v);
    print(v in m/s);
}

7.1 Phase 1: Lexical Analysis

The lexer reads the source one character at a time and groups characters into tokens. It is a hand-coded finite automaton: whitespace and comments are skipped, the longest valid token wins (so <= is one token), identifiers are looked up in the keyword table, and every token remembers its line and column. Numbers keep an exact Fraction value. The lexer does not decide what is a unit: m/s^2 is simply IDENT, SLASH, IDENT, CARET, INT. Lexical errors (illegal character, unterminated string or comment, malformed number, bad escape) are recorded and scanning continues, so one run reports all of them. The demo program produces 46 tokens; the first line becomes UNIT IDENT(h) ASSIGN INT(3600) IDENT(s) SEMI.

7.2 Phase 2: Syntax Analysis

The parser is recursive descent, with one method per grammar rule in Section 6.2 and the two unit rules built in. When it meets a token that cannot continue the current rule, it records an error that names the expected token, then skips ahead to the next ; or } (panic-mode recovery) and continues, so one run lists several real syntax errors. The output is an abstract syntax tree with no punctuation in it: the shape of the tree already says how the expression is grouped.

7.3 Phase 3: Unit and Type Checking

The checker walks the tree bottom-up and computes the type of every node from the types of its children (Figure 2). Where scales differ, it inserts an explicit Convert node with an exact factor; where an int is used as a float, it inserts a Cast. It also keeps a stack of scopes for declared names, checks function calls for argument count and types, checks that functions with a result type return on every path, and produces warnings for unused variables and unreachable code. The --ast output for the demo program shows the result:

Let(name='v')
  Binary(op='/')  : km/h
    Var(name='d')  : km
    Var(name='t')  : h
Print(label='m/s')
  Convert(from_scale=0.2777777777777778, to_scale=1)  : m/s
    Var(name='v')  : km/h

7.4 Phase 4: Intermediate Code

The intermediate code generator lowers the checked tree to three-address code: one operation per line, at most two inputs and one output, with temporaries named t1, t2 and so on. if and while become labels and conditional jumps, and && and || become jumps so that the right side is only evaluated when needed. Units are gone at this point: a conversion is just a multiplication, marked ; convert.

func main():
    d = 90.0
    t = 1.5
    t1 = d / t
    v = t1
    print v "km/h"
    t2 = v * 0.2777777777777778   ; convert
    print t2 "m/s"
    return

7.5 Phase 5: Optimization

The optimizer runs several small passes and repeats them until nothing changes (a fixed point): constant folding, constant and copy propagation, conversion fusion (two conversions in a row become one multiplication by the product of their exact factors), algebraic simplification (x + 0, x * 1), branch folding for constant conditions, removal of unreachable instructions, jump clean-up, and dead-code elimination. Knowledge is discarded at every label, because a label is a point where control can arrive from elsewhere. For the demo program, eight instructions become three in two rounds:

func main():
    print 60.0 "km/h"
    print 16.666666666666668 "m/s"
    return

7.6 Phase 6: Code Generation

The code generator translates three-address code into bytecode for a stack machine. Each instruction becomes a few stack operations: t3 = t1 * t2 becomes LOAD t1, LOAD t2, MUL, STORE t3. Every variable and temporary gets a numbered slot in its function's frame, and labels are turned into absolute addresses in a second pass. A unit conversion is PUSH factor, MUL, when the optimizer has not already folded it away.

== main  (0 params, 0 local slots)
  0000  PUSH   60.0
  0001  PRINT  "km/h"
  0002  PUSH   16.666666666666668
  0003  PRINT  "m/s"
  0004  RET

7.7 Phase 7: The Virtual Machine

The virtual machine is a fetch-decode-execute loop. Each function call pushes a frame holding its local slots, its operand stack and its instruction pointer; RET pops the frame and hands the result to the caller. The machine keeps its own list of frames instead of using Python's call stack, so very deep recursion is reported as a clean Lumen error (more than 5,000 nested calls) and never crashes Python. A step limit of 10,000,000 instructions catches infinite loops. Runtime errors (division by zero, square root of a negative number, call stack too deep, step limit) carry the source line. The demo program prints 60.0 km/h and 16.66666667 m/s.

7.8 Diagnostics

Every phase describes a problem the same way: a message, a line, a column, an underline under the exact characters, and when possible a help line that suggests a fix. The checker includes "did you mean" suggestions for misspelled unit and variable names, based on edit distance. For example, a program that writes 5 mtr is told:

examples/err_units.lum:13:15: error: unknown unit 'mtr'
   13 |     let z = 5 mtr;                     // misspelled unit
      |               ^~~
      = help: did you mean 'm'?

8.3 Other Error Classes

The example err_units.lum makes six different unit mistakes in one program, and one run reports all six: a length where a speed is required, metres plus seconds, a bare number for a time, an impossible conversion of length to seconds, a misspelled unit, and a comparison of a length with a time. Other examples cover dosing (dosing_bug.lum, a time passed as a body weight), currencies (currency_bug.lum, rupees added to dollars without a rate), and every lexical, syntax, scope, return, recursion and runtime error class.

9. Correctness and Safety

A compiler that rejects correct programs or changes their meaning is worse than none. Table 6 lists the safeguards built into the design.

Table 6: Correctness safeguards
SafeguardEffect
Exact rational scalesConversion factors are fractions until the final step; chained conversions are fused into one exact factor, rounded once.
Shared arithmeticThe optimizer evaluates constants with the same function the VM uses, so folding cannot change a result.
Trapping operations keptDivision or modulo that might fail is never folded or removed as dead code, so a division by zero still happens at run time.
Join points resetConstant knowledge is discarded at every label, so a loop variable is never treated as a constant.
No error cascadesAn erroneous expression gets the error type and silences everything built from it.
Bounded executionOwn frame list (5,000 nested calls) and a 10,000,000-step limit; deep nesting in the source is a clean compile error.
No tracebacksEvery user mistake becomes a located diagnostic with an exit code; Python exceptions never reach the user.

10.1 Results Reproduced in This Study

The full suite was run for this study with Python 3.12.4 and reported 187 passed, with no failures and no skipped tests. Two tests deserve particular mention. A differential test runs 21 example programs with and without the optimizer and requires identical output, which is the main evidence that the optimizer is safe. An opcode test compiles a program that converts m/s to km/h and checks that its bytecode uses only ordinary stack instructions (PUSH, LOAD, STORE, arithmetic, comparisons, jumps, CALL, RET, PRINT), which is the evidence that units do not reach run time.

10.2 What the Tests Do and Do Not Show

The tests check specific behaviour with exact expected outputs, including the exact wording and position of error messages, so a regression in any phase is caught. They do not include randomly generated programs (property-based testing or fuzzing), so unusual combinations of features are only as well covered as the hand-written cases. The opcode test checks one program, not every example. These gaps are listed in Table 10.

11.2 Zero Run-Time Cost

The claim that units cost nothing at run time can be shown directly. The program examples/zero_cost.lum declares a speed in km/h and initialises it with 10 m/s:

let v: km/h = 10 m/s;           // source
t1 = 10.0 * 3.6   ; convert      // IR: the conversion is one multiplication
print 36.0 "km/h"               // optimized: the conversion is gone

The conversion is checked at compile time, becomes a single multiplication, and is folded into the constant 36.0. Nothing about units is left for the virtual machine to do.

11.3 Effect of the Optimizer

Figure 5 shows the number of three-address instructions before and after optimization for seven example programs. Programs dominated by constants and unit conversions shrink a lot (20 to 6 for optimizer_demo). Programs whose values depend on input to a function or on a loop, such as fact and primes, do not shrink at all, because the optimizer is deliberately conservative: it only folds what it can prove.

11.4 Cautions

These measurements come from one machine and one Python version and should be read as an order of magnitude, not a benchmark. The large input was generated and is repetitive, so it exercises the compiler evenly but is not typical of hand-written code. The virtual machine is written in Python and is far slower than native code; its speed was not a goal of the project and was not compared with other languages.

12. Contributions and Novelty

None of the ingredients is new: dimensional analysis, syntax-directed type checking, three-address code, constant folding and stack machines are all established techniques [1], [2]. The contribution of Lumen is putting them together in one small language that is designed around units from the start, with a complete compiler that a student can run, read and explain. Table 9 summarises it.

Table 9: Contributions of Lumen
ContributionDescription
Units in the type of every numberQuantities, unit types for variables and functions, declared units and declared base dimensions such as currencies.
Compile-time dimension algebraAn S-attributed checker that adds, subtracts and compares dimension vectors, with exact automatic conversion.
Context rules for unit syntaxA name after a number is a unit; a unit continues over * and / only through known units.
Zero run-time cost, demonstratedUnits erased after checking; conversions fused and folded; a test checks the bytecode's opcode set.

Real failures reproducedThe Mars Climate Orbiter and Gimli Glider bugs, plus dosing and currency mistakes, rejected at compile time.

Novelty qualification. Lumen is a course project. It does not claim to replace F# or production unit libraries, and it makes no claim of research-level novelty.

13. Limitations

The limitations below were found by reading the code and by running the examples. Some are deliberate scope decisions and some are gaps.

Table 10: Limitations, impact and suggested direction
LimitationImpactSuggested direction
Checking covers one program. The Mars failure crossed two programs through a data file.Lumen rejects a bare number entering a typed function, but cannot detect a human writing the wrong unit (12.5 N*s when the file held lbf·s).Typed file formats or interface declarations that carry units between programs.
No offset units (°C, °F).Temperatures need a point-versus-difference distinction that scale factors cannot express.Affine types: a temperature point and a temperature difference as separate kinds.
Dimensions, not quantity kinds.Torque and energy are both kg·m²/s² and cannot be told apart; mcg/kg cancels to a plain number.Named quantity kinds on top of dimensions, as proposed by McKeever [3].
Integer exponents only; ^ needs a literal.Units such as Hz1/2 cannot be written.Rational exponents in the dimension vector.
No unit-polymorphic functions.fn square(x) must be written once per unit.Unit variables and inference across calls, as in F# [13].
Floating-point last-bit differences.A fused conversion uses one exact factor instead of two rounded ones, so a result can differ in the last bit from a hand calculation.Document it; optionally keep exact fractions to run time for printed results.
Python virtual machine.Programs run far slower than native code.An LLVM IR or x86-64 back end from the existing three-address code.
Documents say slightly more than one test shows.The team notes say the opcode check runs "on every example"; the test checks one program.Parametrize the opcode test over all 34 examples.
No property-based or fuzz tests.Rare combinations of features are only covered by hand-written cases.Generate random well-typed programs and compare optimized and unoptimized output.

14. Future Work and Scope for Improvement

14.1 Language

  • Temperature and other offset units through separate kinds for points and differences.
  • Quantity kinds so that torque and energy, or concentration and plain ratios, are kept apart.
  • Unit-polymorphic functions with unit variables, such as fn square<U>(x: U) -> U^2.
  • Arrays and records whose elements carry units.

14.2 Compiler

  • A native back end emitting LLVM IR or x86-64 assembly from the existing three-address code.
  • Global optimizations across basic blocks using data-flow analysis, and loop-invariant code motion.
  • SSA form for the intermediate representation, which would simplify propagation and dead-code elimination.

14.3 Learner Experience

  • A step-through view in the playground that highlights the tokens, tree nodes and instructions for a selected line.
  • Editor integration that underlines unit errors while typing.

14.4 Verification

  • Property-based and fuzz testing of the lexer, parser and checker.
  • Differential testing on every example, and the opcode test parametrized over all programs.
Table 11: Suggested roadmap
HorizonImprovementExpected benefit
Short termParametrize the opcode and differential tests over all examples; fix the documentation claim.Closes the gap between the documents and the tests at low cost.
Medium termQuantity kinds; offset units; property-based tests; step-through view in the playground.Covers the most common real unit mistakes still missed.
Long termLLVM back end; unit-polymorphic functions; typed interfaces between programs.Moves Lumen from a teaching compiler towards practical use.

15. Conclusion

Lumen addresses a problem that every engineer meets sooner or later: the computer cannot tell metres from seconds, and unit mistakes have destroyed a spacecraft and stopped the engines of an airliner. By making the unit part of the type of every number, Lumen turns those mistakes into compile-time errors with a precise location and a suggested fix. By converting with exact fractions and erasing units after checking, it gives that safety without any cost while the program runs.

The compiler implements every classical phase by hand, and each phase has a real job: the parser solves the problem of telling a unit from a variable, the checker is a textbook S-attributed definition over dimension vectors, and the optimizer is what makes the zero-cost claim measurable. The work is verified by 187 passing tests and golden outputs for 34 programs, and a 1,600-line program compiles in under 50 milliseconds. The limits are stated plainly: one program at a time, no temperatures, dimensions rather than quantity kinds, and a Python virtual machine. Each of these has a clear next step, set out in Section 14.
